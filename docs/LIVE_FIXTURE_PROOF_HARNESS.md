# Opt-In Live Fixture Proof Harness

**SentinelForge** is the submitted product repository. The participant-owned [`Aayushashsahu/sentinelforge-incident-fixture`](https://github.com/Aayushashsahu/sentinelforge-incident-fixture) repository remains an external integration target; it is not copied into this repository and is never treated as product source.

`server/sentinelforge/githubFixtureProof.live.test.ts` is disabled by default. It runs only when `RUN_LIVE_FIXTURE_GITHUB_PROOF=1` is explicitly set and then requires server-side `GITHUB_SCRATCH_PR_TOKEN`, the exact `GITHUB_SCRATCH_OWNER=Aayushashsahu`, the exact `GITHUB_SCRATCH_REPO=sentinelforge-incident-fixture`, and an exact fixture-only `GITHUB_SCRATCH_CONFIGURED_CAPABILITIES` declaration for `contents:write` plus `pull_requests:write`. Generic first-party MCP investigation reads retain their existing `GITHUB_READ_TOKEN` client. Fixture-proof evidence reads are instead performed only by `fixtureProofServerEvidence.ts`, after persisted mission/action/fingerprint validation, by injecting `GITHUB_SCRATCH_PR_TOKEN` into its dedicated read client. Model-issued action-bound fixture `get_file` requests are refused and cannot fall back to the generic credential. The declaration proves only the local configuration claim; it does not prove the effective remote token permission. Secrets, provider authorization headers, cookies, and token values are never written to source, test output, or mission evidence.

When separately authorized and explicitly enabled, the harness composes the existing real SentinelForge Investigator, Repair Engineer, fixture-gate approval capture, durable approval persistence, same-turn continuation bridge, immutable executor, audit persistence, allowlists, and write-capability policy. It requires the exact `release-manifest.json` transformation `1.3.0` → `1.4.0`, can create at most one deterministic branch, one commit, and one **open, unmerged** PR, and never merges or deletes that PR.

The harness fails closed before any protected GitHub write if the configured capability is absent, malformed, cross-repository, or mismatched to the protected operation. Immediately before a write it also verifies the immutable target and file, approval correlation, repair fingerprint, idempotency, and current base/content SHA. The exact GitHub endpoint remains the final enforcement point: **effective remote capability remains unverified until that endpoint returns**, and a `403` is persisted only as sanitized terminal evidence without retry. Read access, ownership, rulesets visibility, and a complete fine-grained-token manifest are not used as substitutes for remote acceptance; the manifest remains explicitly unverified by this REST flow. It also does **not** demonstrate sandbox verification: the real repair path remains sandbox-gated, and the harness must be enabled only under a separate live-proof authorization.

For fixture approval capture, the model does not define the target and does not acquire the mandatory repository evidence. After an action is staged, the server derives the canonical owner, repository, base reference, permitted artifacts, and expected versions solely from immutable action intent. It reads only `package.json` and `release-manifest.json` with the action-bound scratch client, verifies the exact versions `1.4.0` and `1.3.0`, persists distinct `SERVER_ORCHESTRATED` evidence markers and audit events, and refuses a failed or mismatched read without advancing that artifact’s flag. Provider-visible context states that this server evidence exists; it does not fabricate provider MCP read calls. The provider receives only `fixture_github_pr_gate`, which accepts only exact proof identifiers and is eligible only when both exact server-orchestrated evidences exist for the same persisted action. SentinelForge persists an approval checkpoint only when a genuine provider approval-required event binds the gate to the exact provider session, turn, thread, and gate tool-call ID. A model-invoked gate alone is never authority to continue or write.

| Persisted evidence category | Source label | Truthful meaning |
| --- | --- | --- |
| Canonical package verification | `SERVER` / `SERVER_ORCHESTRATED` | The server used the action-bound scratch credential to verify `package.json` version `1.4.0`; this is not a provider MCP call. |
| Canonical manifest verification | `SERVER` / `SERVER_ORCHESTRATED` | The server used the action-bound scratch credential to verify `release-manifest.json` version `1.3.0`; this is not a provider MCP call. |
| Fixture gate invocation and approval pause | `PROVIDER` | TrueForge invoked the non-mutating `fixture_github_pr_gate` and emitted the correlated `tool.approval_required` event. No provider file read is claimed. |

Provider session history can serialize the same logical gate or approval pause more than once. Before fixture approval-capture validation, SentinelForge preserves every raw provider event payload unchanged and constructs a separate normalized view. The only permitted propagated values are the capture-route session ID and the documented parent session-history `turn_id` envelope. A raw child `turn_id` and its parent-envelope value must agree when both exist. Thread, tool-call, required-action, source-event, tool-name, tool-server, arguments, and lifecycle payload values are never inferred from event order, timestamps, a neighboring record, or a shared session.

The strict validator consumes normalized data only after each normalized field has recorded its provenance. Gate identity is the complete `session_id`, `turn_id`, raw `thread_id`, `tool_call_id`, and source event ID; approval-pause identity additionally includes the provider `required_action_id`. Lifecycle records may use the documented parent-envelope turn ID, but a missing raw gate or approval-pause thread remains unavailable and fails closed. Missing values, conflicting values, a second gate call, a second required action, an unrelated or malformed model tool call, an out-of-order event, or mismatched approval tool-call correlation remain fail-closed. Replaying identical history after a durable checkpoint is an idempotent no-op; no local reconstruction may fabricate approval, provider, or file-read evidence.

| Audit view | Purpose | Permitted interpretation |
| --- | --- | --- |
| Raw provider history | Preserves every returned event representation unchanged | Shows exactly what the provider returned, including serialized duplicates and omitted child correlation fields. |
| Normalized provider history | Adds only documented parent-envelope turn context and capture-session context, with per-field provenance | Is a distinct validation view; it does not replace raw history or invent thread, tool-call, required-action, source-event, tool, server, argument, or lifecycle data. |
| Canonical logical history | Validates exact approval correlation | Treats only fully identical raw-and-normalized correlated representations as one logical gate, pause, initialization, or terminal event. |
