# GitHub Write-Capability Evidence Policy

SentinelForge distinguishes **configured capability**, **remote endpoint enforcement**, and a **complete token permission manifest** at the fixture GitHub execution boundary. Metadata reads, contents reads, pull-request reads, repository ownership, and rulesets visibility do not demonstrate that the server-side credential may create a branch, update a file, or open a pull request.

The server-only harness accepts a narrowly scoped configuration declaration only when it names the immutable fixture repository and both exact capabilities: `contents:write` and `pull_requests:write`. That establishes **CONFIGURED = VERIFIED** for the corresponding final local guard; a missing, read-only, mismatched, or other-repository declaration remains blocked. Branch creation and the exact `release-manifest.json` update require the configured `contents:write` declaration; pull-request creation requires configured `pull_requests:write`.

GitHub does not expose a general, complete fine-grained-token permission manifest in this API flow. Therefore **FULL_PERMISSION_MANIFEST = UNVERIFIABLE** and **EFFECTIVE = UNVERIFIED** until the exact GitHub write endpoint responds. The configuration declaration does not guarantee acceptance and is never synthesized from a read response. Immediately before a write, SentinelForge still validates the immutable target, exact operation and file, approval correlation, proposal fingerprint, idempotency, current base/content SHA, and configured capability; GitHub then remains the final remote enforcement point.

When configuration is absent, mismatched, or malformed, the executor refuses before network I/O. Genuine write requests that later fail retain the pre-existing terminal partial-state behavior and sanitized status, allowed response headers, and GitHub error evidence; no Authorization header, token, cookie, or complete permission-manifest claim is persisted.
